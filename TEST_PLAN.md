# Тестовая модель MVP

## 1. Критические пользовательские сценарии

### 1.1. Аутентификация и сессии
- Регистрация нового пользователя с ролью `user` или `manager`.
- Вход пользователя: получение access token и refresh token.
- Обновление access token через `/auth/refresh` и корректная работа cookies.
- Разлогин и очистка клиентской сессии.
- Работа гостевого режима без сохранения пароля.

### 1.2. CRUD для карточек и списков
- Создание карточек в собственном списке.
- Получение списка карточек по id с проверкой доступа.
- Удаление личной карточки только владельцем.
- CRUD-ограничения на групповые карточки: только менеджер группы может удалять.
- Фильтрация, сортировка и пагинация карточных списков.

### 1.3. Работа с файлами
- Загрузка файлов только разрешённого типа и размера.
- Получение информации о собственных файлах с предзапрошенным URL.
- Удаление файлов только владельцем.
- Отображение списка файлов для списка карточек только владельцем.

### 1.4. Интеграции
- Внешний генератор карточек через LLM.
- Внешний погодный API.
- Объектное хранилище S3 для сохранения файлов.

## 2. Бизнес-правила и ограничения

- Электронная почта пользователя уникальна.
- Только менеджер может искать пользователей по e-mail.
- Только владелец списка может просматривать личный список.
- Гостевой пользователь не может загружать файлы или просматривать приватные ресурсы.
- Только пользователь с ролями и членством группы может работать с групповыми ресурсами.
- Запросы сортировки/фильтрации допускают конкретные поля и граничные значения.
- Файлы принимаются только форматов jpeg/png/pdf/txt и не больше 10 МБ.
- Внешние сервисы должны обрабатываться как отказ и давать понятную ошибку клиента.

## 3. Области повышенного риска

### 3.1. Аутентификация и сессии
- Проверка токенов `access`/`refresh`.
- Обработка истечения сессии и автоматический refresh.
- Защита cookie `httponly` и `samesite`.

### 3.2. Роли / права доступа
- Разграничение `user` и `manager`.
- Доступ к группам и карточкам только членам.
- Сонеречение доступа к чужим данным через прямые запросы.

### 3.3. Работа с файлами
- Валидация MIME-типа и размера.
- Генерация безопасных ключей и предзапрошенных URL.
- Удаление файлов только владельцем, независимо от параметров.

### 3.4. Интеграции API
- Работа с внешней LLM-генерацией карт.
- Обработка таймаута и некорректного JSON.
- Работа с погодным API при ошибках 404, 502, 504.

## 4. Тестовая инфраструктура

### 4.1. Тестовое окружение
- Отдельный тестовый конфиг backend.
- Тестовая база данных SQLite in-memory для unit/integration.
- Отдельный `requirements-test.txt`.

### 4.2. Изолированная база и фикстуры
- Автоматическое очищение состояния между тестами.
- Поскольку используется async DB, фикстуры работают через rollback.

### 4.3. Мокирование внешних зависимостей
- Моки для вызовов S3.
- Моки для HTTP-запросов в LLM и погодный сервис.
- Фронтенд: глобальный `fetch` и локальное хранилище.

### 4.4. Метрики качества
- Backend: минимальное покрытие 80% по критическим доменам.
- Frontend: модульные и пользовательские сценарии для ключевых страниц.
- Разделение быстрых unit-тестов и длительных E2E.

### 4.5. Структура тестов
- `back/tests/` — backend unit/integration.
- `front/src/__tests__/` — frontend модульные и сценарные.
- `front/e2e/` — E2E проверка маршрутов и авторизации.

### 4.6. Конвенции именования
- `test_*.py` для Python.
- `*.test.tsx` для React.
- `*.spec.ts` для E2E.
- По имени файла явно видно покрытие: `test_auth.py`, `test_files.py`, `test_services.py`.
